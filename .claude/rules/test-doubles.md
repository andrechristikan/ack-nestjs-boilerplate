# Test doubles

- Real, each built with its own dependencies under this split: the `Helper*Service` classes and every `*.util.ts` class under `src/`.
- Doubled: every other collaborator, `MessageService` and `PaginationService` included; `ConfigService` is `buildConfigService` (`test.unit.config.helper.ts`) holding every key a real helper or util reads; `stubConfigValues` (same file) re-keys the built double inside an `it` for a subject that reads config per call (a queue factory).
- A real helper's random, id, or argon2 method is stubbed with `vi.spyOn`, argon2 excepted where hashing is the subject; a clock read runs under `vi.useFakeTimers()` and `vi.setSystemTime()`; a randomly encrypted value or cursor is decrypted with the real helper and the plain value asserted.
- A `src/` branch a spec reaches only by stubbing another real-helper method is dead code, never kept behind a stub: a `src/` change deletes it; on the coverage path it is a recorded defect (`testing.md`, Unit).
- A spec asserts the subject's result and the arguments reaching a double, at least once per method (another branch test of that method may assert the call by count); it asserts a call on a real helper or util only through a `vi.spyOn` stub it installed, and takes no expected value from a copy of a helper's or util's logic.
- Per layer: a service asserts the calls on its own module's doubled collaborators and on the other modules' services it injects, the exception per branch, and, in an `*InTx` method, each call on the `tx` it was given; a use case the shaping, the service call sequence, the effects and activity entries it adds, and, when it opens a transaction, the `*InTx` calls on one `tx` and the mapped write conflict; a use case that is one service call the arguments passing through; an HTTP use case the mapped unique collision and slug retry exhaustion; a queue class each declared scheduler's id, repeat options, job name, data, and options, through `onModuleInit`; an effect builder the queue, name, data with every encrypted field, priority, and key; a cache class the keys and leases it builds and the TTLs it reads; `CacheService`, writing on the cache client, the command, key, JSON value, and `PX` TTL it sends and the failure handling (`cache.md`), the `RedisCacheClient` client doubled; a service's `readThrough` call its key, schema, TTL, lease, and the loader's repository read; a guard transport behaviour; an interceptor or filter the envelope and headers; a DTO per `dto.md`; an exception its five fields. A controller, processor, repository, contract, or module is no unit subject.
