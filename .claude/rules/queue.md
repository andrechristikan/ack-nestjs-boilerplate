# Queues and notifications

BullMQ uses the producer and processor connections `QueueModule.forRoot()` registers in `common.module.ts` (two `BullModule.forRootAsync`); never open another Redis client.

## Where things live

- `src/queues/` is the framework layer: `EnumQueue`, `EnumQueuePriority`, and `EnumQueueJobState` (`enums/queue.enum.ts`; BullMQ's `JobState` is type-only, so a job-state comparison or argument uses this enum, never a string), `QueueConfigKey` and `QueueProcessorConfigKey` (`constants/queue.constant.ts`), `@QueueProcessor()`, `QueueProcessorBase`, `QueueException`, `IQueueResponse`. No processor lives here.
- `<module>.domain.module.ts` registers each owned queue with `BullModule.registerQueueAsync({ name: EnumQueue.<member>, configKey: QueueConfigKey, useClass: <Module>[<Concern>]QueueFactory })` and exports `BullModule`. The factory (`factories/<module>[.<concern>].queue.factory.ts`, implements `RegisterQueueOptionsFactory`) sets `attempts`, `backoff`, `keepLogs`, and removal ages from `queue.*` config, and no `connection`.
- `queues/<module>[.<concern>].queue.ts` is one class per registered queue, provided and exported by the domain module. `@InjectQueue`, the BullMQ `Queue` type, `EnumQueuePriority`, `jobId`, `deduplication`, `add`, `upsertJobScheduler` appear under `src/modules/` only there and in `src/modules/health/indicators/health.queue.indicator.ts`, which reads depth only.

## Enqueuing

A domain or processor service calls a named queue-class method that takes domain values, builds the typed payload, and passes the job name, priority, and options it owns. A `jobId` or `deduplication` id is a `<Module>*JobIdPattern` `{token}` constant in `<module>.constant.ts`, filled in the queue class through `HelperStringService.fillPattern`. The queue class encrypts a sensitive field (generated password; verification, reset, invite, or review link; recipient email; device notification tokens) with `HelperEncryptionService`, the root secret, the module's `*EncryptionPurpose`, and as context the id it belongs to: the recipient's user id, or the invite reference for an invitee with no account (`NotificationEmailQueue.sendWorkspaceInviteUnregistered`). The field is `encrypted<Field>`: job data sits in Redis, readable in BullBoard. A failed `add` maps to no typed exception and answers 500 (`exceptions.md`, The filter chain). A re-enqueue under a fixed `jobId` decides by `getState()` (`sendPublishTermPolicy`, `src/modules/notification/queues/notification.queue.ts:542-606`): no job, or a completed or unknown one once removed, is added; failed is retried with `resetAttemptsMade`; waiting, prioritized, delayed, active, or `waitingChildren` answers `TermPolicyPublishInProgressException` (409), as does a `JobNotInState` retry error; any other retry error is `AppUnknownException`.

The producer takes the preflight decision once, at enqueue: who receives the job, at which address, on which channels after the user's notification preferences, to which device tokens, and the bound of a recipient set. It rides in job data as a required non-null field; the processor reads it there and never re-reads the subject (user, device, setting) to decide. The producer reads this snapshot before any write that does not depend on it, so a failed read leaves nothing written (`forgotPassword`, `src/modules/user/domains/user.password.domain.ts:484`); a snapshot that reads the row the write returns is read after it. A recipient set too large for a payload carries a fixed bound from a stable column, never the current time. Live by design: step state the job records (`completedSteps`, `encryptedPendingTokens`, `TermPolicyRecipient` `sentAt`), a scheduler sweep whose cutoff is relative to now (`expireStaleInvites`, `cleanupStaleTokens`), and the idempotent `cleanupTokens` purge.

## Processors

`@QueueProcessor(EnumQueue.<member>, options?)` extends `QueueProcessorBase` (`src/queues/bases/queue.processor.base.ts`), whose constructor takes `SentryService`. The base owns `process(job)` (`:32`): job-log lines (start, input metadata without `job.data`, success with the returned `IQueueResponse`) and the try/await/catch. Its catch writes the one failure line and the one error log (`Queue job failed`, `:57`, the one log-and-rethrow `logging.md` allows), rethrows `QueueException`, `AppBaseException`, or `UnrecoverableError` as is, and wraps anything else in `AppUnknownException`. Subclasses implement `protected abstract handle(job): Promise<IQueueResponse>` (`:30`) as a dispatcher: switch on `job.name` against `Enum<Module>[<Channel>]Process` (`<module>.enum.ts`, the job names), await a processor-service method (never a bare `return this.service.x()`), map a hopeless failure to BullMQ's `UnrecoverableError` there. The processor service owns no business rule; it calls a domain and throws only `QueueException` (`exceptions.md`). `onFailed` (`:72`) reports to Sentry once, on the last attempt (`attemptsMade >= maxAttempts` or `UnrecoverableError`), skipping a `QueueException` whose `isFatal` is false; retries run either way. A processor or processor service adds no logger or log-and-rethrow. A job may run more than once (automatic retry, BullBoard retry, `getState` re-publish); its handler is safe to repeat and reaches the same decision on every attempt.

In `<module>/interfaces/`, the envelope is `I<Module>[<Channel>][Bulk]QueuePayload<T>` and the data is `I<Module><Action>Payload`, `I<Module><Action>EncryptedPayload` once a field is encrypted. Renaming a queue, a job name, or a payload field changes every producer, processor, and payload type in the same change. Procedure: `.claude/skills/ack-build/references/add-queue.md`.

## Notifications

Two channels, each with its own queue, processor, and processor service: email through `AwsSESService`, push through `FirebaseService`. A request never sends inline. `Notification<Concern>Domain` writes the job's `Notification` rows and fans out; `NotificationEmail*Domain` and `NotificationPush*Domain` send. A notification job runs named steps (`EnumNotificationStep`): `NotificationQueue` generates every row id at enqueue, the rows are written in one `NotificationRepository.createMany`, a retry skips each step recorded in `completedSteps`, and a channel job's `jobId` is `NotificationStepJobIdPattern`. A recipient with no address or token is a no-op, not an exception. An email body is a Handlebars template under `src/modules/notification/templates/`, uploaded to SES by `NotificationTemplate*Domain` and seeded (`seeding.md`); a send names the template and passes `templateData`. The main queue forwards ciphertext unchanged; each channel domain decrypts immediately before its SES or FCM call, an email value into `templateData` only. `FirebaseService.sendMulticast` returns `failureTokens` (invalid tokens, purged by the cleanup job) and `retryTokens` (a `FirebaseRetryableTokenCodes` code, a token failure with no code, or a rejected chunk); any other code, a payload error included, counts in `failureCount` only, neither purged nor retried; the push job keeps them as `encryptedPendingTokens`, a retry sends only to those, and the push `sentAt` is stamped only once none is pending. A decryption failure is unrecoverable: the processor rethrows `HelperDecryptFailedException` as `UnrecoverableError`. Procedure: `.claude/skills/ack-build/references/add-notification.md`.
