# Security

MFA, session invalidation, sign-in, and authorization: `auth.md`. The activity log: `activity-log.md`.

## Credentials

A credential: a password hash or generated password; a TOTP secret, pending secret, backup code; a raw access, refresh, verification, reset, or invite token; an API key secret, encryption root, JWT private key, presign signature.

- Never in a log line, an error message, `JSON.stringify`, a URL path, activity metadata, a Sentry attribute, or `request.<field>`. Redaction (`logging.md`) is only a safety net.
- A plaintext credential enters a database row, cache entry, or job payload only sealed: a value only compared (backup code, token, API key secret, the session jti as `Session.jtiDigest`, an MFA challenge as `MfaChallenge.tokenHash`) as its SHA-256 hash, a value read back (TOTP secret, queued password, link, or OTP, the challenge's push token under `MfaChallengeEncryptionPurpose`) encrypted. A passkey public key and a WebAuthn challenge are public values, stored plain. In memory it rides plain; on the wire, only what the response schema declares.
- A notification recipient's email and device tokens in `Outbox.data`, a `snapshot` included, are encrypted against the recipient's user id (`notification.md`).

## Cryptography

- `node:crypto` runs only through the `Helper*` services, DER-to-PEM key framing included (`HelperEncryptionService.derBase64ToPem`). A token, code, password, or key draws from `HelperStringService` / `HelperNumberService`; a row id is `DatabaseUtil.createId()`.
- `HelperEncryptionService.aes256Encrypt` / `aes256Decrypt(value, secret, purpose, context)`: AES-256-GCM, an HKDF-SHA-256 key over the root, a per-payload salt, and `purpose`, with `context` as authenticated data. `purpose` is one constant per use, owned by the encrypting module (`MfaTotpSecretEncryptionPurpose`); `context` is the owning id, except the cursor token, which uses the fixed `PaginationCursorEncryptionContext` because a token has no owner.
- Root secrets (`APP_ENCRYPTION_SECRET_KEY`, `MFA_ENCRYPTION_KEY`) are 48 random bytes (64 base64url characters), separate roots, generated by `pnpm generate:secret` into `keys/`.
- Hashing is SHA-256 (`HelperHashService.sha256Hash`) for lookups, bcrypt for passwords. A secret comparison is `HelperHashService.sha256Compare` (`timingSafeEqual`); `===` is the defect.

## Request store

Per-request state lives in `RequestStoreService`, keyed by `*StoreKey` constants; add a key, never a second store. `IRequestApp` carries the transport only (`id`, `correlationId`). Each module owns its context: its guard or middleware translates a credential or header into `I<Module>[<Concern>]Context` under its own `<Module>[<Concern>]ContextStoreKey`; every reader takes the context, and no code stores a JWT or provider payload or reads `request.user` (`eslint.md`, Move to ESLint). The JWT guards also write the kit's `RequestActorStoreKey` (the user id) for the logger, audit stamping, and the per-user throttle. A guard, middleware, or interceptor injects it, and the kit reads it (`DatabaseExtensionFactory` audit stamping, `MessageService`, the logger mixin); a param decorator: `guards.md`. A service, use case, effect builder, or processor never reads it (a list use case's `PaginationStoreKey` merge is a write, `pagination.md`): the controller passes the contexts down (`http.md`, `service.md`), and the raw refresh token lives in `IAuthJwtRefreshContext` only, never in a job payload or a log. `RequestRequestIdMiddleware`, first in the `RequestMiddlewareModule` chain, alone writes `req.id`, `req.correlationId`, and both id store keys (`logging.md`). `IRequestContext.requestLog` holds the client IP, user agent, and geo-location, resolved once per request (`request.request-log.middleware.ts`) and never re-resolved. The client IP is `req.ip` under `trust proxy` (`src/configure.ts:38`).
