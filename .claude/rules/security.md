# Security

## Credentials

A credential: a password hash or generated password; a 2FA secret, pending secret, backup code; a raw access, refresh, verification, reset, or invite token; an API key secret, encryption root, JWT private key, presign signature.

- Never in a log line, error message, `JSON.stringify`, URL path, activity metadata, Sentry attribute, or `request.<field>`. Redaction (`logging.md`) is only a safety net.
- A plaintext credential enters a database row, cache entry, or job payload only sealed: a value only compared (backup code, token, API key secret) as its SHA-256 hash, a value read back (2FA secret, queued password or link) encrypted. In memory it rides plain; on the wire, only what the response schema declares.

## Cryptography

- `node:crypto` runs only through the `Helper*` services, DER-to-PEM key framing included (`HelperEncryptionService.derBase64ToPem`). A token, code, password, or key draws from `HelperStringService` / `HelperNumberService`; a row id is `DatabaseUtil.createId()`.
- `HelperEncryptionService.aes256Encrypt` / `aes256Decrypt(value, secret, purpose, context)`: AES-256-GCM, an HKDF-SHA-256 key over the root, a per-payload salt, and `purpose`, with `context` as authenticated data. `purpose` is one constant per use, owned by the encrypting module (`AuthTwoFactorSecretEncryptionPurpose`); `context` is the owning id, except the cursor token, which uses the fixed `PaginationCursorEncryptionContext` because a token has no owner.
- Root secrets (`APP_ENCRYPTION_SECRET_KEY`, `AUTH_TWO_FACTOR_ENCRYPTION_KEY`) are 48 random bytes (64 base64url characters), separate roots, generated by `pnpm generate:secret` into `keys/`.
- Hashing is SHA-256 (`HelperHashService.sha256Hash`) for lookups, bcrypt for passwords. A secret comparison is `HelperHashService.sha256Compare` (`timingSafeEqual`); `===` is the defect. The one exception: the `SessionCache.updateLogin` Lua script compares the stored and candidate jti SHA-256 digests, hashed through `HelperHashService` before the call; the raw jti never reaches Redis.

## Two-factor

`TwoFactor.secret` holds only a confirmed authenticator, encrypted with the two-factor root and the user id. Setup writes `pendingSecret`; confirming moves it into `secret`; disable and admin reset clear both. Setup while enabled consumes a valid backup code by compare-and-set on the stored list, committed before a token is issued. A missing or undecryptable secret raises `AuthTwoFactorSecretUnavailableException` (409).

- A two-factor attempt runs the password attempt flow: a guarded increment (`updateMany` `where attempt < max`) decides; the service counts, enqueues the lockout on a spent budget (Session invalidation), asserts, then verifies.
- `TwoFactor.lastUsedStep` accepts each TOTP step once.
- `loginSetupTwoFactor` reads the challenge without consuming it; only `loginVerifyTwoFactor` claims it, after verification succeeds (`cache.md`).

## Session invalidation

Password change or reset, logout, device removal, self-deletion, two-factor disable or admin reset, a status change to `blocked` or `inactive`, refresh-token reuse, and an admin revoke of one or all sessions each revoke the session rows and enqueue the session cache purge; the JWT guards read the cache, so revocation lands when the job runs. The purge job carries the user id and the exact `ISessionRef[]` the revoke returned, which `SessionCache.deleteLogins` deletes, never a key pattern. Order: commit, enqueue the purge, stage activity rows. Every revoke and rotation `where` carries `isRevoked: false`.

- A spent password or two-factor attempt budget throws its max-attempt exception at once and enqueues `UserQueue.lockout(userId)`: job `lockout` on the `user` queue, payload `{ userId }`; every spent budget enqueues its own job. The request stages its `userReachMax…Attempt` and `userRevokeAllSessions` rows at enqueue. `UserProcessorService.lockout` runs one transaction, the guarded deactivate (stop when already inactive), the session revoke, and the device revoke, then enqueues the session cache purge after commit; revocation lands when the job runs.
- A refresh re-reads the session row, then rotates by compare-and-set on the old `jti` in the database `where` and the cache write; a mismatch is reuse: revoke the session, enqueue its purge.

## Sign-in and authorization

`AuthSocialDomain` verifies Google with `audience` set to its client id and Apple against the set client ids; an unset provider throws its not-configured exception first, rethrown unwrapped by `AuthDomain`. CASL abilities come from the caller's role's `Policy` rows; `@PolicyProtected` names subject and actions. A login stamps the last login inside its transaction (`UserDomain.updateLoginInTx`).

- Role rank is `superAdmin > admin > user` (`EnumRoleType`). An admin-facing write on a role, its policies, or a user (create, role, status, password reset, 2FA reset) refuses a target ranked at or above the actor, except a superAdmin actor on a superAdmin target. No actor edits the role they hold or its policies. A role request DTO's `type` is `admin` or `user`.
- A role with `isImmutable` true cannot be deleted and its `type` cannot change, whoever the actor is. Its `description` and policies stay editable under the rank gates. The role seed alone sets the field, true on `superadmin`, `admin`, and `user`; no request DTO, `IRoleCreate`, or `IRoleUpdate` carries it. `user.default.role` names the sign-up role, one of those immutable roles.
- The term-policy guard compares the user's `TermPolicyUserAcceptance` rows with the latest published policy per required type; a type with no published version needs no acceptance and makes sign-up throw a term-policy exception. Publishing a version archives every earlier published one of its type; readers take the latest published row per type. No per-user acceptance flag, no reset on publish.
- Login answers one invalid-credential error for unknown email, wrong password, and inactive account. Forgot-password and resend-verification answer 200 in every account state, sending only when eligible.
- Self-delete, and 2FA setup and enable while 2FA is off, require the current password of an account that has one. A passwordless account relies on its session.
- An `admin` or `superAdmin` account cannot delete itself.
- A user who owns a workspace with any other member cannot delete their account until they transfer ownership. A workspace with no other member is deleted with the account.
- 429 answers a limit (`UserForgotPasswordRequestLimitExceededException`, `UserVerificationEmailResendLimitExceededException`); 403 a spent attempt budget (`UserPasswordAttemptMaxException`, `AuthTwoFactorAttemptMaxException`).

## Activity log

`ActivityLogDomain.prepare` (`activity-log.domain.ts:213`) validates one entry against `ActivityLogActionContract`; `stagePrepared` (`:238`) puts it on the CLS queue. The HTTP service prepares before the domain write and stages after its commit (`service.md`); a value only the write produces is drawn before it (`DatabaseUtil.createId()`) or prepared after. Every `EnumActivityLogAction` member has a contract row and an `activityLog` i18n key. An action one user takes on another writes two rows: the actor's under the plain action with `targetUserId`, the affected user's under the paired `…ByAdmin` / `…ByOwner` / `…ByInvitee` action with `actorUserId`.

- The activity log is HTTP-only: a job stages no entry. `ActivityLogDomain.flushStaged` (`:252`) runs when an HTTP request settles (`ActivityLogInterceptor`), error path included, while the store holds `RequestLogStoreKey` and `WorkspaceStoreKey`. It draws each row id (`DatabaseUtil.createId()`) and enqueues every row in one `ActivityLogQueue.createMany` job (`QueueBase.addSideEffect`).
- Its processor writes through `ActivityLogRepository.createMany`, a retry only the rows whose id is absent.

## Request store

Per-request state lives in `RequestStoreService`, keyed by `*StoreKey` constants; add a key, never a second store. A class injects it; a param decorator: `guards.md`. `RequestRequestIdMiddleware`, first in the `RequestMiddlewareModule` chain, alone writes `req.id`, `req.correlationId`, and both id store keys (`logging.md`). `RequestLogStoreKey` holds the client IP, user agent, and geo-location, resolved once per request (`request.request-log.middleware.ts`) and never re-resolved. The client IP is `req.ip` under `trust proxy` (`src/configure.ts:39`).
