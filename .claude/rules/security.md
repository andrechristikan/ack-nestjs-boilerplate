# Security

## Credentials

A credential: a password hash or generated password; a 2FA secret, pending secret, backup code; a raw access, refresh, verification, reset, or invite token; an API key secret, encryption root, JWT private key, presign signature.

- Never in a log line, an error message, a `JSON.stringify`, a URL path, activity metadata, a Sentry attribute, or `request.<field>`. Redaction (`LoggerSensitiveFields`, `src/instrument.ts`) is only a safety net.
- A plaintext credential enters a persisted or transported store (a database row, a cache entry, a job payload) only sealed: a value only compared (backup code, token, API key secret) as its SHA-256 hash, a value read back (2FA secret, a queued password or link) encrypted. Inside an in-memory object passed between functions (a domain result, a return value, a method argument) it rides plain. On the wire: only what the response schema declares.

## Cryptography

- `node:crypto` runs only through the `Helper*` services, DER-to-PEM key framing included (`HelperEncryptionService.derBase64ToPem`, `helper.encryption.service.ts:149`). A token, code, password, or key draws from `HelperStringService` / `HelperNumberService`; a row id is `DatabaseUtil.createId()`.
- `HelperEncryptionService.aes256Encrypt` / `aes256Decrypt(value, secret, purpose, context)` (`helper.encryption.service.ts:58`): AES-256-GCM, an HKDF-SHA-256 key over the root, a per-payload salt, and `purpose`, with `context` as authenticated data. `purpose` is one constant per use, owned by the encrypting module (`AuthTwoFactorSecretEncryptionPurpose`); `context` is the id the value belongs to.
- Root secrets (`APP_ENCRYPTION_SECRET_KEY`, `AUTH_TWO_FACTOR_ENCRYPTION_KEY`) are 48 random bytes as exactly 64 base64url characters, separate roots, generated by `pnpm generate:secret` into `keys/`, printed as paths.
- Hashing is SHA-256 (`HelperHashService.sha256Hash`) for lookups and bcrypt for passwords. A secret comparison is `HelperHashService.sha256Compare` (`helper.hash.service.ts:27`, `timingSafeEqual`); `===` is the defect.

## Two-factor

`TwoFactor.secret` holds only a confirmed authenticator, encrypted with the two-factor root and the user id. Setup writes `pendingSecret`; confirming moves it into `secret`; disable and admin reset clear both. Setup while enabled consumes a valid backup code in the same transaction, a compare-and-set on the stored list that commits before a token is issued. A missing or undecryptable secret raises `AuthTwoFactorSecretUnavailableException` (409).

## Session invalidation

Password change or reset, logout, device removal, account self-deletion, the max-attempt password lockout, two-factor disable or admin reset, a status change to `blocked` or `inactive`, refresh-token reuse, and an admin revoke of one or all sessions each revoke the session rows and enqueue the session cache purge; the JWT guards read the cache, so revocation takes effect when the job runs. The purge job carries the user id and the exact `ISessionRef[]` the revoke returned; `SessionCache.deleteLogins` deletes those entries, never a key pattern. Order: commit, enqueue the purge through `QueueBase.addSideEffect` (`exceptions.md`, Side effects), stage activity rows. `isRevoked: false` is in the `where` of every revoke and rotation.

- A refresh re-reads the session row from the database, then rotates by compare-and-set on the old `jti`: the database `where` and the cache write each match it. A mismatch is reuse: revoke the session and enqueue its purge.
- The login cache TTL equals the access-token lifetime (`auth.jwt.accessToken.expirationTimeInSeconds`).

## Sign-in and authorization

The guard stack: `guards.md`. `AuthSocialDomain` verifies Google with `audience` set to its client id and Apple against the set client ids; an unset provider throws its not-configured exception first, rethrown unwrapped by `AuthDomain`. CASL abilities come from the `Policy` rows on the caller's role; `@PolicyProtected` names subject and actions. A login stamps the last login inside its transaction (`UserDomain.updateLoginInTx`, `src/modules/user/domains/user.domain.ts:180`).

- Role rank is `superAdmin > admin > user` (`EnumRoleType`). An admin-facing write on a role, its policies, or a user (create, role, status, password reset, 2FA reset) refuses a target ranked at or above the actor, except a superAdmin actor on a superAdmin target. No actor edits the role they hold or its policies. A role request DTO accepts `type` `admin` or `user` only.
- The term-policy guard compares the user's `TermPolicyUserAcceptance` rows with the latest published policy of each required type; a type with no published version has nothing to accept. Publishing version N moves every earlier published version of that type to `archived`; every reader takes the latest published row per type. No per-user acceptance flag, no reset on publish. Sign-up throws a term-policy exception while a required type has no published version.
- Login answers one invalid-credential error for unknown email, wrong password, and inactive account. Forgot-password and resend-verification answer 200 for every account state and send only when eligible.
- Self-delete, and 2FA setup and enable while 2FA is off, require the current password.
- A limit or lock exception answers 429: `UserForgotPasswordRequestLimitExceededException`, `UserVerificationEmailResendLimitExceededException`, `AuthTwoFactorAttemptTemporaryLockException`.

## Activity log

`ActivityLogDomain.prepare` (`activity-log.domain.ts:213`) validates one entry against `ActivityLogActionContract`; `stagePrepared` (`:238`) puts it on the CLS queue. The HTTP service prepares before the domain write and stages after its commit (`layering.md`); a value only the write produces is drawn before it (`DatabaseUtil.createId()`) or prepared after. Every `EnumActivityLogAction` member has a contract row and an `activityLog` i18n key. An action one user takes on another writes two rows: the actor's under the plain action with `targetUserId`, the affected user's under the paired `…ByAdmin` / `…ByOwner` / `…ByInvitee` action with `actorUserId`.

- The activity log is HTTP-only: a job stages no entry. `ActivityLogDomain.flushStaged` (`:252`) runs when an HTTP request settles (`ActivityLogInterceptor`), error path included, while the store holds `RequestLogStoreKey` and `WorkspaceStoreKey`. It draws each row id with `DatabaseUtil.createId()` and enqueues one job carrying every row through `ActivityLogQueue.createMany` (`QueueBase.addSideEffect`, `exceptions.md` Side effects).
- Its processor writes through `ActivityLogRepository.createMany`, the one `ActivityLog` writer; a retry writes only the rows whose id is absent.

## Request store

Per-request state lives in `RequestStoreService`, keyed by `*StoreKey` constants; add a key, never a second store. A class injects `RequestStoreService`; a param decorator: `guards.md`. `RequestRequestIdMiddleware`, first in the `RequestMiddlewareModule` chain, alone writes `req.id`, `req.correlationId`, and both id store keys (`logging.md`). `RequestLogStoreKey` holds the client IP, user agent, and geo-location resolved once per request (`request.request-log.middleware.ts`); a reader never re-resolves it. The client IP is `req.ip` under `trust proxy` (`src/configure.ts:39`).
